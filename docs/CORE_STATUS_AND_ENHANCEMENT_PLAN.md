## 四、核心短板深度分析

### 4.1 Agent层过于单薄 (最大短板)

**问题**: `CodeWriterAgent`、`CodeReviewerAgent`、`TesterAgent` 三个核心Agent都只是简单的 "prompt + JSON parse" 模式，缺乏智能化逻辑。

**具体表现**:
- `CodeWriterAgent` (75行核心代码): 无代码模板、无增量生成、无上下文感知
- `CodeReviewerAgent` (77行): 审查维度固定、无历史审查记忆
- `TesterAgent` (70行): **仅设计测试用例不执行**，这是最大的功能性缺失

**影响**: Agent层是直接产出代码的层，其薄弱直接导致最终代码质量上限受限。

### 4.2 "设计-执行"断层

**问题**: 系统有完善的"设计"能力（任务拆分、测试设计、质量标准），但"执行"环节断裂。

**具体表现**:
- TesterAgent设计了测试用例 → 无人执行
- QualityCheckerAgent可以编译代码 → 但不在沙箱中运行
- ContractAssembler生成了契约 → 但无运行时契约验证
- MergeEngine合并了代码 → 但无合并后集成测试

### 4.3 MCP生态单向

**问题**: 系统有MCP Server（向外暴露能力），但无MCP Client（消费外部能力）。

**影响**: 无法利用日益丰富的MCP生态（如文件系统、数据库、浏览器、Git等MCP服务）来增强自身能力。

### 4.4 适配器深度不均

**问题**: 13个工具适配器中，仅 `ClaudeCodeAdapter` 和 `OpenClawAdapter` 集成了 `NativeAPIAdapter`，其余11个仍使用基础CLI调用。

**影响**: 大部分工具的结构化输出解析、上下文注入、增量采集能力未启用。

### 4.5 无语义记忆

**问题**: `MemoryStore` 使用JSON文件存储，无向量检索能力。

**影响**: 无法基于语义相似度检索历史任务经验，工具学习的效果受限于精确匹配。

## 五、深化核心能力增强方案 (分3个优先级)

### 🏆 P0 — 立即实施 (预计2-3周)

#### 5.1 实现测试执行引擎

```
新建: src/core/TestRunner.js
```

**目标**: 让 `TesterAgent` 设计的测试用例能够真正执行。

**方案**:
- 创建 `TestRunner` 模块，支持多种测试框架执行 (pytest, jest, go test, mvn test)
- 与 `QualityCheckerAgent` 的编译能力整合
- 在合并后自动运行集成测试
- 测试结果反馈到质量评分

**预期效果**: 质量保障从"静态检查"升级为"动态验证"，完成度 +3%

#### 5.2 实现MCP客户端

```
新建: src/mcp/MCPClient.js
```

**目标**: 能够连接并消费外部MCP服务。

**方案**:
- 实现 stdio 和 SSE 两种传输方式
- 支持动态发现和注册MCP工具
- 将MCP工具纳入 `TaskRouter` 的路由池
- 优先集成: filesystem MCP、git MCP、fetch MCP

**预期效果**: 系统能力通过MCP生态无限扩展，完成度 +2%

#### 5.3 Agent层智能化升级

**目标**: 将三个核心Agent从"prompt+parse"升级为"智能体"。

**CodeWriterAgent 增强**:
- 代码模板库（按语言/框架/模式）
- 增量代码生成（基于已有代码补全而非全量重写）
- 多轮自检与修正

**CodeReviewerAgent 增强**:
- 上下文感知（考虑项目历史代码风格）
- 审查记忆（记住之前的审查反馈）
- 差异审查（只审查变更部分）

**TesterAgent 增强**:
- 自动生成可执行测试代码
- 集成 TestRunner 执行测试
- 测试覆盖率分析

**预期效果**: Agent层完成度从 73.8% 提升到 85%，综合 +2%

### 🎯 P1 — 近期实施 (预计4-6周)

#### 5.4 语义记忆与向量检索

```
新建: src/core/VectorMemoryStore.js
```

**目标**: 基于 embedding 的语义记忆系统。

**方案**:

- 替换 MemoryStore 中的精确匹配为语义匹配

**预期效果**: 工具学习精度提升 40%+，完成度 +2%

**目标**: 从 Provider 到 CLI/WebUI 的全链路流式输出。

**方案**:

- CLI/WebUI 通过 SSE 实时展示生成过程
- 合并引擎流式输出合并过程

**预期效果**: 用户体验大幅提升，完成度 +1%

#### 5.6 Token预算与成本管理

```
新建: src/core/BudgetManager.js
```

**目标**: 全局token预算管理和成本追踪。

**方案**:
- 每次任务设定token预算上限

**预期效果**: 成本可控，完成度 +1%

#### 5.7 智能重试与错误分类

**目标**: 基于错误类型的智能重试策略。

- 指数退避 + 抖动
- 重试时自动调整参数（降低temperature等）
- 与熔断器联动

**预期效果**: 健壮性提升，完成度 +1%

#### 5.8 全适配器NativeAPI集成

**目标**: 将 `NativeAPIAdapter` 推广到所有13个适配器。

**方案**:
- 为每个适配器编写 `CapabilityProbe` 配置
- 启用 `StructuredOutputParser` 解析

## 九、结论

Qidi Agent 的核心管线（拆分→分发→执行→质检→合并→报告）**已完整实现并可用**，综合完成度 **84%**。上一轮优化将管线各模块的质量从 ~80% 提升到 ~88%，解决了"有没有"的问题。

当前的核心瓶颈不再是管线缺失，而是 **"深度不足"**：
1. **Agent层太薄** — 代码生成/审查/测试三个核心Agent只是prompt包装
2. **执行断层** — 设计了测试不执行、设计了契约不验证
3. **生态孤立** — 有MCP Server无MCP Client
4. **记忆原始** — JSON存储无语义检索

下一步的增强方向应从"补管线"转向"加深度"，优先实施 P0 的三项增强（TestRunner、MCPClient、Agent智能化），预计可将完成度提升到 92%，使系统从"可用"变为"好用"。
