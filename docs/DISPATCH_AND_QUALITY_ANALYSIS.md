# 分发机制与产出质量深度分析报告

## 一、分发是怎么分发的？

### 1.1 整体流程

```
用户任务 → TaskSplitterAgent (LLM拆分) → 子任务列表
                                           ↓
                                    TaskScheduler (依赖调度)
                                           ↓
                                    TaskExecutor (单任务执行)
                                           ↓
                              ┌────────────┴────────────┐
                              ↓                          ↓
                        隐私模式                    传统模式
                              ↓                          ↓
                     TaskRouter.routeTask()     codeWriter + 多工具并行
                              ↓                          ↓
                    选择1个工具适配器           _dispatchToAdapters()
                              ↓                          ↓
                    adapter.execute()          各工具独立执行
                              ↓                          ↓
                    CLI命令调用工具             _mergeToolOutputs()
                              ↓                          ↓
                    收集stdout/文件             MergeEngine合并
```

### 1.2 拆分阶段（TaskSplitterAgent）

**实际做法**：
1. 将用户任务描述 + 复杂度分析 + 项目契约信息拼接成 prompt
2. 发送给 LLM（Ollama/OpenAI/DeepSeek）请求拆分为 3-10 个子任务
3. LLM 返回 JSON 格式的子任务列表，包含：id、title、description、role、dependsOn、acceptanceCriteria、requiredContracts、producesContracts
4. 进行自检（覆盖率验证、依赖图验证、循环依赖检测）
5. 如果验证不通过，最多重试 2 次
6. 如果 LLM 返回格式无效，降级到规则模板拆分（按复杂度 low/medium/high 给出 1/3/7 个子任务）

**关键问题**：
- 拆分质量完全依赖 LLM 能力，本地小模型（如 qwen2.5:7b）拆分质量不稳定
- 契约信息是"建议性"的，不强制约束后续执行
- 实验数据显示：T1（架构设计）通常得分 87-97，但 T2-T5 得分仅 17-20

### 1.3 调度阶段（TaskScheduler）

**实际做法**：
1. 拓扑排序：按 `dependsOn` 关系确定执行顺序
2. 每轮获取所有"就绪"任务（依赖已完成的 pending 任务）
3. 就绪任务可以并行执行（但实际是串行 for 循环，非真并行）
4. 每个任务最多重试 2 次
5. 核心角色（architect、code_writer）失败时严格模式直接报错
6. 非核心角色（code_reviewer、tester、quality_checker）失败时继续执行

**关键问题**：
- `executeLoop` 中的 `for (const task of readyTasks)` 是串行 `await`，不是真并行
- 失败重试时不改变任务描述，只是重新执行相同的 prompt

### 1.4 路由分发阶段（TaskRouter）

这是**核心分发逻辑**，支持 6 种路由策略：

| 策略 | 分发方式 | 隐私性 | 实际效果 |
|------|---------|--------|---------|
| round_robin | T1→工具A, T2→工具B, T3→工具C, T4→工具A... | 高 | 每个工具只看到部分任务 |
| capability | 按语言/框架/复杂度/角色评分，选最高分工具 | 高 | 理论最优，但能力表是静态硬编码 |
| top_n | 选前N个最优工具并行执行 | 中 | 多工具同时执行同一任务 |
| manual | 人工预定义路由表 | 高 | 最精确但需人工配置 |
| broadcast | 所有工具执行所有任务 | 低 | 传统模式，用于质量对比 |
| synchrony | 根据历史同步强度动态选择 | 中 | S>0.7单工具，0.4<S<0.7双工具，S<0.4单工具 |

**隐私模式下的分发**：
1. `TaskRouter.routeTask(task)` 根据策略选择 1 个工具
2. 构建"隐私任务描述"：只包含当前子任务的 title、description、role、language、frameworks、验收标准
3. 调用 `adapter.execute(taskDescription, options)` 执行
4. 工具通过 CLI 命令执行（如 `openclaw agent -m "任务描述"`）
5. 从 stdout 或输出文件中收集结果
6. 提取代码块

**关键问题**：
- **工具间完全隔离**：每个工具只拿到自己的子任务描述，不知道其他工具在做什么
- **无共享上下文**：工具不知道前序子任务的产出代码
- **契约不传递**：虽然拆分时定义了 `requiredContracts`/`producesContracts`，但分发时不传递这些信息

### 1.5 工具适配器执行

以 `OpenClawAdapter.execute()` 为例：
1. 创建工作目录 `workspace/openclaw/{taskId}/`
2. 将任务描述写入 `task.md`
3. 执行 CLI 命令：`openclaw agent -m "任务描述"`（超时 5 分钟）
4. 从 stdout 收集输出，或从 `output.md` 文件读取
5. 用正则提取代码块
6. 收集生成的文件
7. 返回统一格式结果

**关键问题**：
- 工具收到的只是纯文本描述，没有项目结构、没有已有代码
- 工具的输出格式不统一，代码提取依赖正则匹配
- 超时 5 分钟可能不够复杂任务

### 1.6 合并阶段（MergeEngine）

**实际做法**：
1. 按 filePath 分组各工具的代码块
2. 单版本文件直接使用
3. 多版本文件：
   - 3+ 版本：三路合并（提取契约→比较签名→AI合并）
   - 2 版本：两路合并（AI对比选择）
   - 多版本：两两合并
4. 语义冲突检测（按语言的正则匹配未定义函数/类）
5. 合并后验证：编译检查（gcc/python/node）、语法检查（括号匹配）、契约一致性
6. 质量评估（基于冲突标记数、符号完整度、原始评分加权）

**关键问题**：
- 契约提取是**正则匹配**，不是 AST 解析，准确率有限
- 三路合并假设有"基准版本"，但实际上各工具是独立产出，没有共同基准
- AI 合并依赖 LLM 理解代码语义，但 LLM 可能不理解完整项目上下文
- 编译检查只是 `--check` 级别，不执行代码

## 二、最终形成高质量代码的可能性

### 2.1 实验数据证据

| 任务类型 | 成功率 | 质量评分范围 | 典型问题 |
|---------|--------|-------------|---------|
| 简单函数（GCD） | 100% | 71-97 | 无明显问题 |
| HTTP服务器 | 67% | 38-45 | 语言识别错误（Python任务被识别为javascript） |
| 完整Web应用 | 100%* | 17-87 | T1得分87，T2-T5仅17-20，代码不兼容 |

*注：100%成功率是指"任务执行完成"，不代表产出代码可用

### 2.2 产出代码不兼容的实证

以 task_1782960536642（投标系统）为例：

- **T1 产出** (`output_1782960616267_1.py`)：使用 Flask-SQLAlchemy，定义了 User/Project/Bid 三个模型，关系完整
- **T2 产出** (`output_1782960678301_1.py`)：使用原生 sqlite3，只定义了 users 表，没有 Project/Bid 表，字段结构完全不同
- **T5 产出** (`output_1782960860880_1.py`)：测试代码 `from app import app, db, User, Project, Bid`，但 T2 的代码中根本没有 Project/Bid 模型

**结论**：T1 设计了架构，但 T2 的工具完全不知道 T1 的设计，独立产出了不兼容的代码。T5 的测试代码假设了 T1 的接口，但实际代码是 T2 的不兼容版本。

### 2.3 质量评分不可靠

- 质量评分由 LLM 给出，本地小模型评分虚高
- 无实际代码执行验证
- 合并质量评估基于启发式规则（括号匹配、符号计数），不是真正的质量度量
- 实验报告中 T2-T5 得分 17-20，但状态标记为"✅ 成功"

### 2.4 形成高质量代码的概率评估

| 场景 | 成功概率 | 原因 |
|------|---------|------|
| 单文件简单函数 | 80-90% | 单工具即可完成，无需合并 |
| 多模块中等项目 | 30-40% | 模块间接口可能不匹配 |
| 复杂全栈应用 | 10-20% | 多工具独立产出几乎不可能自动拼合 |
| 需要严格类型一致性的项目 | <10% | 契约提取是正则级别，无法保证类型兼容 |

## 三、核心问题根因分析

### 问题1：上下文断裂

**现象**：工具执行子任务时，不知道前序子任务的产出代码
**根因**：隐私模式下 `_buildPrivacyTaskDescription()` 只传当前任务信息，不传 previousCode
**影响**：各工具产出的代码接口不兼容

### 问题2：契约不约束

**现象**：拆分时定义的 `requiredContracts`/`producesContracts` 在执行时被忽略
**根因**：`_executePrivacyMode()` 不读取也不传递契约信息
**影响**：工具不知道需要实现什么接口、可以依赖什么接口

### 问题3：合并非真合并

**现象**：MergeEngine 试图合并不兼容的代码
**根因**：各工具独立产出，没有共同的接口基准
**影响**：合并后的代码无法编译/运行

### 问题4：调度非真并行

**现象**：TaskScheduler.executeLoop() 中就绪任务是串行执行
**根因**：`for (const task of readyTasks)` + `await executeFn(task, context)`
**影响**：无法利用多工具并行加速

### 问题5：质量验证不充分

**现象**：质检只做 LLM 评分，不做实际编译/运行
**根因**：质检 Agent 只是发 prompt 给 LLM 评估，不执行代码
**影响**：质量评分虚高，实际代码可能无法运行

## 四、解决方案

### 方案1：契约驱动的分发（解决上下文断裂+契约不约束）

**思路**：在分发子任务时，将该子任务的契约信息（需要实现的接口、可依赖的接口）作为硬约束传递给工具

**实现要点**：
1. TaskSplitter 产出子任务时，同时产出"接口契约定义"（Interface Definition）
2. 分发子任务时，将该子任务的 `requiredContracts`（需要调用的接口签名）和 `producesContracts`（需要实现的接口签名）附加到任务描述中
3. 工具收到的任务描述包含：任务描述 + 必须实现的接口签名 + 可调用的接口签名
4. 合并时，先验证各工具产出是否满足其 `producesContracts`，再按 `requiredContracts` 关系拼装

### 方案2：增量上下文传递（解决上下文断裂）

**思路**：在隐私模式下，将前序子任务的"接口摘要"（不是完整代码）传递给后续子任务

**实现要点**：
1. 每个子任务完成后，提取产出的接口签名（函数签名、类定义、数据结构）
2. 后续子任务的任务描述中包含前序子任务的接口摘要
3. 接口摘要只包含签名，不包含实现，保护隐私

### 方案3：真并行调度（解决调度非真并行）

**思路**：将就绪任务真正并行执行

**实现要点**：
1. `executeLoop` 中使用 `Promise.allSettled` 并行执行就绪任务
2. 设置并发限制避免资源竞争

### 方案4：编译验证门控（解决质量验证不充分）

**思路**：合并后必须通过编译检查，不通过则触发修复

**实现要点**：
1. 合并后执行实际编译（gcc/python -c/node --check）
2. 编译失败时，将错误信息反馈给工具重新生成
3. 通过编译后才标记任务完成

### 方案5：接口适配层自动生成（解决合并非真合并）

**思路**：当各工具产出的接口不完全匹配时，自动生成适配层

**实现要点**：
1. ContractAssembler 已经有 `_suggestResolution` 逻辑
2. 在合并阶段，当检测到接口不匹配时，自动生成适配函数
3. 适配函数将不同签名的函数调用转换为目标签名

## 五、实施优先级

| 优先级 | 方案 | 预期效果 | 实现难度 |
|--------|------|---------|---------|
| P0 | 契约驱动分发 | 确保工具知道需要实现什么接口 | 中 |
| P0 | 增量上下文传递 | 确保工具知道前序产出 | 低 |
| P1 | 编译验证门控 | 确保合并后代码可编译 | 中 |
| P1 | 真并行调度 | 提升执行效率 | 低 |
| P2 | 接口适配层 | 自动修复接口不匹配 | 高 |

---

## 六、总结

当前系统的核心理念"拆分→并行分发→质检→合并"在理论上是合理的，但实现上存在**上下文断裂**和**契约不约束**两个根本性问题，导致各工具产出的代码互不兼容，合并后无法形成可运行的高质量代码。

形成高质量代码的概率：
- 简单任务：80-90%（单工具即可完成）
- 中等任务：30-40%（模块间可能不匹配）
- 复杂任务：10-20%（多工具独立产出几乎无法自动拼合）

最关键的改进是**契约驱动分发 + 增量上下文传递**，确保每个工具不仅知道"做什么"，还知道"需要实现什么接口"和"可以依赖什么接口"。
